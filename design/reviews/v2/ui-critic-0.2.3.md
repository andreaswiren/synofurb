# UI critic, new screens since 0.2.2 (branch tip 03d9d3b), desktop and management-plane web UI

Scope: everything new since `v0.2.2`. Desktop: Find NAS Networks dialog, scan progress panel, results and empty states, Add by IP dialog and its three row kinds, Inspection volumes list and Use column, Setup > Add-ons, Quick setup presets, Confirm "Not touched" and add-on lines. Web: the Add-ons page (cards, install dialog, job, logs, details, remove) and the Updates page (channel, consent, progress, rollback, history) in `apps/mgmt-plane/synofurb_mgmt.py` and `demo/index.html`. Checked against `design/BRIEF-v2.md` and `design/v2/DESIGN-SYSTEM-V2.md`. No gate verdict; nothing written to `design/approvals/`; no code edited; no cargo build.

How I checked: I read the sources; looked at the 20 new committed desktop screenshots; drove the web demo myself with the repo's own tooling (Playwright and `/usr/bin/google-chrome`, `file://` demo, 1280 x 800, 390 x 844, 640 and 320 wide, light and dark, every state listed below, plus two edited copies of the demo with Docker missing and with unhealthy add-ons to reach states the demo does not offer); ran the existing desktop binary (`/tmp/gpui-probe-target/debug/synofurb`, built today, knows the new screens, not rebuilt) at 960 x 640 default and Largest text, light, for 15 screens (my dark run was stopped; dark at default size is judged from the committed dark shots). Every contrast figure is from pixels (dominant background against the farthest text colour in a box). Scratch files are deleted.

## Verdict

The new surfaces are consistent with the system at a glance: tokens, Lucide icons only, Inter and JetBrains Mono, themed scrollbars, 2 px accent focus line on the web, outline tags that hug their content, text contrast at least 6.2:1 in both themes on every pair I measured. The problems are (1) a **regression of last round's Find-table blocker at Largest text**, (2) a literal **"null"** printed in every Updates progress card, (3) **no screenshots at all of the new web pages**, and (4) a cluster of disabled-reason and disclosure gaps on the web that the desktop got right. **Blocking 3, major 6, minor 14.** Release blockers for 0.2.3 are B1, B2 and B3; I would also fix M1 and M2 before tagging.

## Blocking

**B1. Find NAS clips its data at Largest text (regression of the fixed NB1).** `inventory-added`, `inventory-scan-done` and `inventory-scanning` at Largest (960 x 640): the DSM column cuts its text mid-glyph ("7.2.1-6905|", "7.2.2-7280|", no ellipsis), the Status tag "Community-reported" is sliced at the column edge (no right border), "Unknown device" becomes "Unknown d...", the Found-by cell becomes "udp . mdns . ss...". Cause: a trailing actions column (about 135 px wide, empty on most rows) now takes width from the data columns. At default size (960) it is acceptable ("udp . mdns . ssdp . d..."); at Largest it is not. `gui-walk.sh` cannot see this (no scrollbar, content stays inside the page margin), which is exactly the limit I recorded in round 3. Must change: size the actions column to its content (24 px icons, or one overflow menu), give the cells ellipsis, and add a clipping check to the walk (compare cell text against cell width). No committed screenshot shows this state at Largest; the committed Find shots are 1176 x 760.

**B2. The Updates progress card prints the word "null".** Web, Updates page, any running or finished update: under the last step ("Health") the card shows `null` as text (`up-running-light.png`, `up-refused-light.png` in my captures; both themes). Cause: `host.replaceChildren(ul, restarting ? banner(...) : null)` in `watchJob` (`synofurb_mgmt.py`, the `draw` function); `replaceChildren(null)` appends the string "null". The same sentence is then repeated by the step's own message and the refusal banner. One-line fix (filter falsy children); the existing `ui_updates.js` flow test passes with it present, so add an assertion that the card contains no "null". Release blocker: it is on the self-update path of the feature this release ships.

**B3. The new web pages have no screenshots, and the desktop evidence is at non-standard sizes.** `design/screenshots/` has no `mgmt-demo-addons-*` or `mgmt-demo-updates-*` file (the newest `mgmt-demo-*` files are from 1 November, before the Add-ons and Updates pages existed); BRIEF-v2 principle 8 makes screenshots of the real UI the review artifact. On the desktop the 20 new files are 1176 x 760, 1240 x 900 or dialog crops: none is at the 960 x 640 minimum window and none at Largest text, so none could have shown B1. Must change: capture every state in the list at the end of this review, at 1280 and 390 on the web, 960 x 640 default and Largest on the desktop, light and dark.

## Major

**M1. Confirm contradicts itself about the USB disk.** `confirm-not-touched-light.png`: the Preserved card says "Nothing on the disks" while the Erased disks card (red) ends with "Not touched: sde (usb disk)". The safe fact is printed inside the destructive card in 12 px, and the preserved summary is false (sde is preserved). Put the untouched disks in Preserved ("sde, usb disk, not touched"), keep the red card to what is erased. This is the data-loss gate: fix before 0.2.3.

**M2. The Networks dialog clips at Largest.** `dlg-networks` at Largest: the "Recommended" tag is cut at the dialog's right edge, CIDR text wraps ("192.168.1.0" over "/24"), rows differ in height. The dialog is fixed at 640 px with no wrapping rule for the row. The same dialog is clean at default size and in dark.

**M3. Disabled controls on the web do not give their reason to the keyboard, and one never gives it at all.**
* Updates, "Update now" before a check: the reason ("check first") is attached with `tip()` to the disabled button itself; I hovered it in Chrome and no tooltip appears (disabled buttons swallow `mouseenter`). The reason is invisible to mouse, keyboard and touch. The desktop pattern (a visible info button next to the control) is not used.
* Add-ons, card "Install" when Docker is missing: the tip sits on a wrapper `span`; it appears on mouse hover ("Install Docker first." verified) but a disabled button is not focusable, so keyboard and touch users see a greyed button and no reason (`nodocker-light.png`, three cards).
* Install dialog: "Install" starts disabled until the privileges box is ticked, but that box sits below the fold of a 768 px dialog (`addons-install-plex-light.png` shows the disabled button and no reason; the checkbox is visible only after scrolling). Use the existing pattern at `synofurb_mgmt.py:7391` (`aria-disabled` plus a visible reason) or put the reason in text beside the button.

**M4. Why an update failed or rolled back is hover-only on a non-focusable badge.** History table: `tip(badge(...), j.message)` ("update to 0.4.0 failed; rolled back" appears only on mouse hover; I verified `tabIndex = 0` is false for the badge, i.e. not focusable). Keyboard and touch users see "Rolled back" and never learn why. Show the message in the row (it fits as a second line) or make the row expandable.

**M5. Privilege consent differs between the surfaces.** The web install dialog requires "I accept these privileges" (Docker control, host network). The desktop Setup > Add-ons shows tags ("Controls Docker", "Uses NAS network") with info buttons, and Confirm lists the add-ons, but nothing asks the person to accept them; Confirm has three acknowledgements, all about erasing. Portainer is root-equivalent on the unit. The UX critic should rule on it; as a UI matter the two surfaces should behave the same.

**M6. Setup > Add-ons is heavy.** `addons-chosen-light.png`: Portainer carries five elements before its sentence (two neutral outline tags that look like buttons, two (?) buttons, one warning tag, a third (?)). BRIEF-v2: "far too much text" was the owner's complaint. Show one risk tag with one info button per add-on and fold "Needs Docker / Needs Internet" into the add-on's popover.

## Minor

* **m1. Word budget is exempted for add-on prose.** `ui_audit.js` now treats `[data-d]` as data, so add-on summaries, setting labels and notes (the manifest text) are not counted; the audited Add-ons page reads 24 words, but with nothing installed the four card summaries alone are about 50 more (`nodocker-light.png`). On the desktop the `addons` screen budget excludes the four catalog sentences as well. Count manifest text, or cap its length in the manifest tests.
* **m2. `.err` leaks into badges.** The global form-error rule `.err{display:flex;margin:0 0 10px}` (`synofurb_mgmt.py:6077`) applies to `.badge.err`: the "Problem" state tag stretches to 215 px against 82 to 126 px for the others and gains a 10 px bottom margin (`attn-dark.png`). Scope the rule to `.f .err` or similar.
* **m3. Needs-attention duplicates.** An add-on in "needs attention" appears twice on the page: in Installed (with a full icon row) and as an Available card with "Retry". One place, please.
* **m4. Problem details are one click away.** Rows say "Not answering", "Needs attention", "Problem"; the reason ("no space left on device") exists only in the Details dialog.
* **m5. Icon-only action rows.** Six 24 px ghost icons per installed add-on (stop, restart, update, logs, details, remove); each has a tooltip and an accessible name, and keyboard focus shows them, but "update" and "install" use the same download glyph, and at 390 px the row wraps unevenly (Portainer: four on one line, two on the next). Action cells also start at a different x in each row (Docker vs Portainer in `addons-light.png`) because the "Open" button is conditional.
* **m6. Install dialog.** Five identical "Help" buttons (same accessible name for different fields); "Media access: ro" shows the raw value; at 390 px the label and its Help button wrap onto separate lines ("Address clients should use (bridge only)"). Details dialog: an unlabeled "1" chip (the definition revision) next to the status.
* **m7. Job dialog.** Primary "Close" while a job runs (closing leaves it running; say "Hide" or "Run in background"); `<progress>` has no accessible name and the message line is not a live region (the Updates step list has `aria-live`).
* **m8. Update confirm dialog.** The unsigned-release warning (low-emphasis text) sits below the consent checkbox that depends on it; put the warning first, as a warning banner.
* **m9. Focus after a job.** After closing a job dialog with the keyboard the page container (`main#main`, tabindex -1) receives a 2 px accent outline: a full-width line appears at the bottom of the content area (`ad-after-install-light.png`, y = 667). Suppress the outline on that container or move focus to the heading.
* **m10. Narrow reflow.** At 320 px (400 % zoom) the Add-on details dialog lets chips overflow the dialog ("9443/tcp Web UI (self-signed certificate)" ends at x = 348 on a 320 px screen). 390 and 640 px are clean, and so is every page body at 320.
* **m11. Off-scale values.** New CSS and Rust: `.aico` radius 10 px (scale 4, 8, 12), 13 px and 15 px/22 text in `.acard p` and `.dsec h4` (web already uses 13 px 19 times, so this is drift, not a new rule break), `px(10.0)` row padding and `px(28.0)` / `px(30.0)` indents in `screens/addons.rs` and `screens/inventory.rs` (spacing scale 2, 4, 6, 8, 12, 16, 20, 24).
* **m12. Desktop: "Install target" in green.** Inspection marks the disks that will be erased with a green check tag ("Install target", `inspect-volumes-light.png`); green reads as "safe" and on Confirm the same disks are red. Neutral or accent would avoid the contradiction.
* **m13. Desktop: Quick setup layout.** The Storage value wraps and leaves an orphan ("... 10.82" / "TiB"), and the "Storage" label is aligned to the last line, not the first, beside the orphan; this happens at 960 default and in the committed shot (`dlg-quick-addons-light.png`), not only at Largest. Align labels to the first line and keep the figure and its unit together.
* **m14. Desktop: small items.** The Add-a-network field shows a suggested CIDR in the same colour as typed text (reads as a value, not a hint); the actions column mixes two icons ("check again", "remove") with a labelled "Check again" button on the unreachable row; Inspect at Largest overlaps the label's info icon with the tag's icon ("Compatibility", `inspect-light-largest.png`; the same overlap is in the committed 1 November shot, missed last round); the scan panel's track is 1.37:1 / 1.29:1 against the page (the fill is 4.7:1 against the track, so it reads, but the web progress has a 1 px 3.95:1 border and the desktop does not).

## What is right (checked, not assumed)

* **Tokens and icons.** Every colour on the new web pages resolves to the existing theme variables; desktop uses `cx.pal()` roles; icons are Lucide on both (the web falls back to `package` for an unknown add-on icon id, which is the right failure).
* **One primary.** Desktop: Connect (Find), Done (Networks), Add or Done, Next (Add-ons), Use these (Quick setup). Web Updates: Update now; dialogs: one primary each. The web Add-ons page repeats a primary "Install" on every available card (up to four), the same pattern as Mounts' per-row "Mount"; acceptable, noted.
* **Dark mode.** Dialog `#171717`, canvas `#0A0A0A`, accent `#A37BFE` with `#0E0C15` text (6.30:1); states and tags 6.3 to 11.7:1.
* **Focus lines.** Web: 2 px accent outline on inputs, selects, buttons (6.67:1 / 6.30:1); desktop: DEV-UI-22 solid line (not re-shot for the new controls).
* **Scrollbars.** Web: global thin themed scrollbars (`*{scrollbar-width:thin}`, token thumbs, hover state); desktop uses the existing mode.
* **No horizontal scroll on the web** at 1280, 640, 390, 320 on both new pages and their dialogs (the only overflow is m10). The repository's own `ui_audit.js` run (with a Chrome path patched in, nothing else changed) reports no errors, no unresolved strings, no overflow and no external requests.
* **Install, remove and update gates.** Typed phrase for Remove with data deleted (`Type portainer to confirm`, disabled until typed, shown in dark), typed 7-character commit for the Main channel, consent box for unsigned releases, "Update anyway" only after a refusal: all behave as designed, in both themes.
